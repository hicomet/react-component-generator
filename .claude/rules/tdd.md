# TDD Rule

> **이 규칙은 Rigid — 상황에 맞게 변형하지 마라.** 사이클을 줄이거나 순서를 바꾸지 않는다.

## 우선순위

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그쪽이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙이 침묵하는 부분에만 적용한다.

## 1. 적용 기준

### TDD 필수

- 비즈니스 로직
- API (핸들러, 요청/응답 처리)
- 유틸 / 순수 함수
- 버그 수정 (**버그를 재현하는 실패 테스트를 먼저 작성**)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업·스타일)
- SQL

경계가 애매하면 **적용하는 쪽**으로 판단한다.

## 2. RED-GREEN-REFACTOR

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트를 작성한 뒤 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 테스트는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 실패, 오타로 인한 실패는 RED가 아니므로 테스트를 고친다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI:** 지금 테스트가 요구하지 않는 기능, 옵션, 추상화를 넣지 않는다.
- **신규 테스트와 기존 테스트 모두 통과**하는지 전체 실행으로 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green 상태를 유지**한다. 리팩터링 후 테스트를 다시 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작이 필요하면 RED로 돌아간다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 3. 삭제 강제

- 테스트 전에 프로덕션 코드를 먼저 작성했다면 **그 코드를 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지.** 주석 처리, 별도 파일 보관, 복사해 두기 모두 해당한다.
- 삭제한 코드를 보고 다시 쓰는 것도 금지. 테스트가 이끄는 설계로 새로 작성한다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드가 가장 자주 깨진다. 테스트도 단순하니 작성 비용이 거의 없다. |
| 나중에 추가하겠다 | 나중은 오지 않는다. 사후 테스트는 이미 구현에 맞춰져 실패하지 않으므로 아무것도 증명하지 못한다. |
| 시간이 없다 | 디버깅과 회귀 수정이 더 오래 걸린다. 테스트 없는 속도는 빚이다. |
| 삭제하면 낭비다 | 매몰 비용이다. 검증되지 않은 코드를 유지하는 비용이 재작성 비용보다 크다. |
| 프로토타입이다 | 프로토타입은 프로덕션으로 가는 경우가 많다. 버릴 코드라면 삭제 비용도 없다. |

## 완료 전 체크

- 모든 새 동작에 대해 **RED를 실제로 실행해 확인**했는가
- GREEN은 **최소 구현**인가
- 전체 테스트가 통과하는가
- 테스트보다 먼저 쓴 프로덕션 코드는 **삭제**했는가
